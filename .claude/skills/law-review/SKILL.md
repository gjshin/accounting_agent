# 법령 검토 + 인터뷰 절차

`korean-law-reviewer` 에이전트는 사용자에게 직접 질문할 수 없다. 결론을 좌우하는 사실이 빠지면 에이전트는 보고서 대신 `[인터뷰 요청]`을 돌려준다. 메인 세션이 그 질문을 사용자에게 묻고, 답을 **같은 에이전트**에 이어서 보낸다.

## 1. 의뢰

1. 사용자의 요청을 쟁점 단위로 나눈다. 쟁점이 여러 개면 쟁점마다 에이전트를 하나씩 병렬로 실행한다.
2. 쟁점마다 맡길 에이전트를 정한다.
   - 세법·외부감사법·상법·자본시장법 등 법령 쟁점 → `korean-law-reviewer`
   - 회계처리 판단·감사절차 쟁점 → `accounting-wiki-reviewer` (인터뷰·보고 처리는 `accounting-review` 스킬과 같다)
   - 한 거래에 둘 다 걸리면(예: 주식 저가 양수도의 회계처리와 부당행위계산 부인) 쟁점을 나눠 두 에이전트를 함께 실행한다.
3. 각 에이전트에는 사용자가 준 사실관계 전체와 해당 쟁점만 넘긴다. 사용자가 준 문장은 고치지 말고 그대로 옮긴다. 사용자가 거래일·사업연도를 말했으면 반드시 함께 넘긴다.
4. 사용자가 "인터뷰 없이", "가정으로 진행", "인터뷰 생략"이라고 했거나 테스트 시나리오를 돌리는 경우에는 의뢰문 끝에 `인터뷰 생략`을 붙인다.
5. 의뢰문 끝에 항상 다음 문장을 붙인다: "최종 보고 전에 `.claude/agents/<맡긴 에이전트 이름>.md`의 '검토 의견 작성법', '판단 흐름표 작성법', '최종 보고 양식'을 읽고 그대로 따른다." 세션 중에 절차서가 바뀌면 에이전트가 예전 양식으로 쓸 수 있어서다.
6. 에이전트를 실행할 때 사용자에게 한 줄로 알린다. 예: "세무 쟁점 1개와 회계 쟁점 1개를 나눠 맡겼습니다. 정보가 부족하면 질문드리겠습니다."

## 2. 인터뷰 요청을 받았을 때

에이전트 결과가 `[인터뷰 요청]`으로 시작하면 보고서로 취급하지 않는다.

1. **에이전트가 여러 개면 모든 결과를 기다린 뒤 질문을 한 번에 모은다.** 법령 에이전트와 회계 에이전트가 같은 사실(예: 특수관계 여부, 거래일)을 물으면 하나로 합치고, 어느 쟁점에서 나온 질문인지 표시한다.
2. 질문을 사용자에게 보여 줄 때 함께 적는다.
   - 쟁점 요약, 적용 법령과 기준 시점, 에이전트의 잠정 판단 (한두 줄)
   - 질문마다 "왜 필요한지" 한 줄 (에이전트가 적은 '필요한 이유'를 쉬운 말로 줄여서)
   - "모르면 '모름'이라고 답해 주시면 기본 가정(○○)으로 진행합니다"
3. 묻는 방법
   - **선택형 질문**(선택지 2~4개)은 AskUserQuestion 도구로 묻는다. 한 번에 최대 4개. 선택지에 없는 답은 사용자가 '기타'로 직접 쓸 수 있다.
   - **서술형 질문**(금액, 일자, 지분율, 계약 문구, 지배구조 설명 등)은 일반 메시지로 번호를 붙여 묻고 사용자 답을 기다린다.
   - 선택형과 서술형이 섞이면 서술형을 메시지로 먼저 묻고, 선택형은 AskUserQuestion으로 묻는다.
4. 사용자가 답하면 SendMessage로 **처음 실행한 같은 에이전트**에 답을 보낸다 (새 에이전트를 띄우면 앞서 조회한 내용이 사라진다). 두 에이전트가 같은 질문을 했으면 양쪽에 모두 보낸다. 보내는 형식:

```
[인터뷰 답변] 회차: 1/2
질문 1 답: (사용자 답변 원문)
질문 2 답: 모름 → 기본 가정으로 진행
...
위 답변을 '제공된 사실(인터뷰 답변)'으로 반영해 이어서 진행해 줘.
```

   - `korean-law-reviewer` 는 4-1단계부터, 답으로 거래일·사업연도가 바뀌면 3단계(기준 시점 확정)부터 다시 진행한다.
   - `accounting-wiki-reviewer` 는 3-1단계부터 다시 진행한다.
5. 에이전트가 회차 2/2 인터뷰를 다시 요청하면 같은 방식으로 한 번 더 묻는다. 그 뒤에도 질문이 오면 사용자에게 묻지 말고 "남은 공백은 가정으로 두고 최종 보고서를 작성해 줘"라고 에이전트에 보낸다.

## 3. 최종 보고

0. **보고서는 세 문서로 나눠 파일로 저장하고, Word로 바꿔 사용자에게 보낸다.** 요약만 전하고 끝내지 않는다.
   - 폴더: `reports/YYYY-MM-DD-<주제 영문 요약>/` (점검 시나리오는 `agent-tests/<에이전트>/results/` 아래). 쟁점이 여러 개면 쟁점별로 폴더를 나눈다.
   - **`reports/` 폴더는 저장소에 올리지 않는다.** 실제 질의·고객 건의 기록과 보고서는 이 폴더에만 두고 커밋·푸시하지 않는다(저장소 설정에서 제외해 둠). 클라우드 세션에서는 세션이 끝나면 이 폴더가 사라지므로, 아래처럼 파일을 반드시 사용자에게 보내 내려받게 한다.
   - 폴더명·파일명과 커밋 메시지에는 회사명이나 고객을 알아볼 수 있는 이름을 쓰지 않는다. 주제는 회계·세무 쟁점으로만 적는다(예: `sublease-ifrs18`).
   - `00-record.md`: 작성일, 질의 원문, 인터뷰 질문과 답변, 맡긴 에이전트를 적는다.
   - `raw-report.md`: 에이전트 최종 보고를 **고치지 않고** 그대로 저장한다.
   - `python3 tools/split_report.py <폴더>/raw-report.md <폴더>` 로 `01-opinion.md`(검토 의견서), `02-memo.md`(감사 조서 메모 또는 내부 검토 메모), `03-email.txt`(이메일 축약 의견)를 만든다. 구분선이 없다는 오류가 나면 에이전트에 SendMessage로 "최종 보고 양식의 세 문서 구분선을 넣어 다시 보내 줘"라고 요청한다.
   - `python3 tools/md_to_docx.py <폴더>/01-opinion.md <폴더>/01-opinion.docx --subtitle "<회계위키 근거 검토 / 법령 근거 검토>"`, 같은 방식으로 `02-memo.docx`를 만든다. 회사 양식은 `templates/reference.docx`가 있으면 자동으로 쓴다.
   - 메인 세션이 원문을 따로 대조했으면 그 결과를 `00-record.md` 끝에 한 줄 덧붙인다.
   - SendUserFile로 `01-opinion.docx`, `02-memo.docx`, `03-email.txt`를 보낸다. 이메일 본문은 대화창에도 그대로 붙여, 사용자가 바로 복사할 수 있게 한다.
1. 파일을 보낸 뒤 검토 의견서 '1. 요약'을 중심으로 결론, 기준 시점, 핵심 근거, 회사 처리에서 고칠 점과 세액·금액 영향, 결론을 바꿀 추가 확인 사실을 전달한다.
2. 법령 에이전트를 여러 개 돌렸으면 보고서끼리 금액 기준이 맞는지 확인한다.
   - 같은 자산의 시가·평가액·차액을 보고서마다 다르게 잡았는지 본다(예: 한 보고서는 할증 후 시가, 다른 보고서는 할증 전 금액).
   - 다르면 사용자에게 전하기 전에 해당 에이전트에 SendMessage로 기준이 다른 이유를 묻는다. 세법상 시가와 상법상 공정가액처럼 기준이 달라야 하는 정당한 이유가 있으면, 그 구분을 보고서에 밝히게 한다. 이유가 없으면 맞춘 금액으로 고쳐 달라고 한다.
3. 법령 에이전트와 회계 에이전트를 함께 돌렸으면 두 결론이 서로 맞는지 확인한다.
   - 법령 내부 검토 메모의 '회계·감사 영향'이 회계 검토 의견서의 결론·회계처리와 맞는지
   - 법령 보고서의 'accounting-wiki-reviewer 에 넘길 사항'이 회계 검토 의견서에서 다뤄졌는지
   - 두 쟁점을 회사에 한 번에 회신해야 하면 두 이메일 축약 의견을 하나의 메일 본문으로 합친 초안(`03-email-combined.txt`)도 만들어 보낸다.
   - 어긋나면 사용자에게 그대로 보여 주고, 어느 쪽 사실관계·가정 차이 때문인지 밝힌다.
4. 인터뷰 답변이 결론에 어떻게 반영됐는지 한 줄로 밝힌다. 예: "양수인이 특수관계인이라는 답변 때문에 시가와의 차이가 부당행위계산 부인 대상이 됐습니다."
5. 에이전트가 가정으로 진행한 항목은 따로 모아 "확인되면 결론이 바뀔 수 있는 사항"으로 보여 준다.
6. 세무 결론은 신고·처분 결과를 보장하지 않는다는 한계를 한 줄로 덧붙인다.
7. 사용자는 코드 설명보다 회계·세무 실무 관점의 설명을 원한다. 도구 이름이나 내부 절차는 설명하지 않는다.

## 4. 넘긴 사항 자동 처리와 통합 보고서

에이전트 보고서에 다른 에이전트에게 넘길 사항이 있으면 **사용자에게 묻지 않고** 바로 이어서 맡긴다. 이렇게 이어지는 의뢰가 모두 끝나면 통합 보고서를 만든다. `accounting-review` 스킬로 시작한 건도 이 절차를 따른다.

1. 넘길 사항 찾기: 최종 보고를 받을 때마다 다음을 읽는다.
   - 회계 검토 의견서 '9. 관련 사항'의 "korean-law-reviewer 에 넘길 사항"
   - 법령 내부 검토 메모 '4. accounting-wiki-reviewer 에 넘길 사항'. 법령 검토 의견서 '9. 관련 사항'에 같은 내용이 있으면 하나로 본다.
2. 거르기: 아래 항목은 넘기지 않는다. 대신 그 쟁점 폴더의 `00-record.md`에 사유를 한 줄 남긴다.
   - 이미 끝났거나 진행 중인 다른 쟁점 보고서에서 다룬 항목. 어느 보고서에서 다뤘는지 적는다.
   - 사용자 질의와 거리가 먼 일반 사항. 예: 질의와 무관한 다른 세목, 단순 절차 안내.
3. 자동 의뢰: 남은 항목을 받을 에이전트별로 묶는다. 한 묶음은 에이전트 하나에 맡기고, 서로 독립이면 여러 에이전트를 병렬로 실행한다. 의뢰문에는 다음을 넣는다.
   - 질의 원문과 인터뷰로 확인된 사실. 원문을 고치지 않는다.
   - 앞선 보고서들의 확정 결론과 주요 금액. 앞선 보고서의 금액·날짜를 그대로 옮긴다.
   - 넘긴 사항 원문과, 넘긴 에이전트·보고서 이름
   - 다른 에이전트가 맡은 범위는 다루지 말라는 문장
   - `인터뷰 생략`: 사용자 인터뷰는 첫 의뢰에서 끝났다. 빈 사실은 가정으로 두고, 그 가정은 통합 보고서에 모은다. 그래도 `[인터뷰 요청]`이 오면 "남은 공백은 가정으로 두고 최종 보고서를 작성해 줘"라고 보낸다.
   - 1-5의 양식 문장
   - 사용자에게는 한 줄만 알린다. 예: "세무 검토가 넘긴 회계 사항 2건을 회계 에이전트에 이어서 맡겼습니다."
4. 연쇄 한도
   - 자동 의뢰는 처음 의뢰부터 두 단계까지만 한다(처음 의뢰 → 1차 넘김 → 2차 넘김).
   - 세 번째 단계의 넘길 사항은 의뢰하지 않고 통합 보고서 '7. 추가 검토 제안'에 적는다.
   - 앞에서 넘긴 항목이 되돌아오면 다시 넘기지 않는다.
5. 진행 중 전달
   - 각 보고서는 3번 절차대로 쟁점별 폴더에 세 문서로 저장하고 Word로 바꾼다.
   - 연쇄가 이어지는 동안에는 파일을 보내지 않고, 끝난 쟁점과 이어서 맡긴 쟁점만 한두 줄로 알린다.
   - 보고서끼리 금액·날짜·전제가 어긋나면 3번의 2·3 절차로 먼저 맞춘다.
6. 통합 보고서: 남은 넘길 사항이 없거나 한도에 이르면 메인 세션이 작성한다.
   - 폴더: `reports/YYYY-MM-DD-<사안 영문 요약>-integrated/`
   - `00-integrated.md`의 구성
     1. 질의 요지와 검토 범위. 질의 원문 요약과 함께 "쟁점 | 맡은 에이전트 | 의뢰 경로(처음 의뢰 / ○○ 보고서가 넘김) | 폴더" 표를 둔다.
     2. 종합 결론표: 쟁점 | 결론 | 핵심 근거 | 확정도
     3. 회사가 할 일: 회계처리와 공시, 세무조정과 신고, 감사 대응을 시점 순으로 적는다. 분개·세무조정 금액은 개별 보고서의 금액을 그대로 쓴다.
     4. 쟁점 간 정합성: 같은 날짜·금액·전제를 쓰는지 확인한 결과와, 어긋난 곳이 있으면 그 이유
     5. 확인되면 결론이 바뀔 수 있는 사항: 모든 보고서의 가정을 모으고, 영향받는 쟁점을 적는다.
     6. 회사에 요청할 자료: 중복을 없애고 한 목록으로 적는다.
     7. 추가 검토 제안: 한도를 넘은 넘길 사항과 2번에서 거른 사항
     8. 첨부 목록: 쟁점별 검토 의견서·메모 파일명
